# Installed-client smoke tests: Minecraft 1.14–1.14.4

The identical intermediary JAR built from implementation commit
`bfa85625b10a2709fc01af26eef9e80df791dcb9` had SHA-256
`909b2299eed92d71c054bc9ddb4829235f560c657fab79a60f91a78354a06eec`.
It was installed on each version with Fabric Loader 0.20.1, Java 8
(8.0.504+1), Linux and a software Xorg/Mesa display. Every client applied its
required Mixin, joined the same single-player world (created in 1.14 and
upgraded in order) and displayed generated terrain on maps held in the following
arrangements:

These are partial local-player smoke tests. Additional per-version left-handed,
opposite-hand, untagged-item and first-person comparisons are listed below;
unlisted versions and cases remain NOT RUN. Missing-data null behavior, complete
lighting, movement, OpenGL state restoration,
first-person regression, multiplayer and independent visual acceptance remain
outstanding. The software display had no audio device and the offline clients
could not retrieve online profiles. Complete the full runtime matrix on the
final artifact before release.

## Unsupported-version launch

A headless Linux Fabric Loader 0.20.1 launch installed this same JAR into a
Minecraft 1.15 client using Java 8. Fabric exited with status 1 during mod
resolution and explicitly identified 1.15 as unsupported; Mixin initialization
was not reached. The [launch log](1.15-unsupported-neighbor.txt) records the
actual rejection. This checks the declared version guard for that client, not
a forced installation with the guard bypassed. A Java 7 launch is recorded below.

## Java 7 launch

A headless Linux launch placed the same candidate JAR in a Minecraft 1.14
Fabric Loader 0.20.1 profile using Zulu OpenJDK 7.0.352. The process exited
with status 1 because the loader's entry class requires class-file version 52
(Java 8); [the launch log](1.14-java7-rejected.txt) records the error. The
loader stopped before it could inspect the mod's own metadata, so this is a
loader/runtime rejection rather than an independent test of that metadata.

The Java 7 distribution's SHA-256 was checked against [vendor metadata](https://api.azul.com/metadata/v1/zulu/packages/f436b3cb-0115-4814-b7fa-e180747bd68f):
`8a7387c1ed151474301b6553c6046f865dc6c1e1890bcf106acc2780c55727c8`.

The initial 1.14 attempt used a newer option-file format that left the client
[right-handed](1.14-initial-right-hand.png). The fixture was restored, the legacy
left-hand option set, and all checks below repeated. The initial image is not
counted as left-handed evidence.

## Additional 1.14 left-handed and first-person checks

With the same candidate JAR, the left-handed local client displayed terrain in
the [main hand](1.14-extra-left-main.png), [off hand](1.14-extra-left-off.png),
and [both hands](1.14-extra-left-both.png). Terrain remained visible with stone
in the opposite hand for the [main-hand map](1.14-extra-left-main-stone.png)
and [off-hand map](1.14-extra-left-off-stone.png). An [untagged filled map](1.14-extra-left-untagged.png)
remained usable without a crash. Older clients can resolve a missing map ID to
map 0, so this does not establish the missing-data null path, which remains NOT RUN.

The [candidate first-person view](1.14-extra-firstperson.png) was compared
with the same Fabric Loader profile [without the candidate JAR](1.14-extra-firstperson-no-mod.png)
using a copy of the saved world. In the 540 by 440 pixel map crop at `(370, 60)`
the mean absolute channel difference was 1.147 on a 0–255 scale;
97.450% of pixels differed by at most 10 levels per channel,
with a maximum of 18. The views were not pixel-identical, and this single
comparison does not establish complete first-person regression coverage.
